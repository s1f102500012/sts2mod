# 审计规范

本目录用于提供可重复执行的实现证据，不用于证明实现没有风险。审计者应把结论
分为以下三级，并为每项结论提供对应证据：

1. **已复现**：包含执行命令、输入、完整错误或状态输出和运行环境。
2. **代码可证明**：包含具体方法、守卫条件、完整调用链和可达性说明。
3. **理论风险**：当前没有复现或无法从现有调用链证明可达。

“使用私有成员”“补丁入口较多”和“依赖异步状态机 IL”足以证明版本敏感性，
但不能单独证明全局劫持、崩溃、死锁、联机分叉或对第三方模组的定向行为。
这些结论分别需要无条件状态写入、可达异常链、锁依赖环、双端状态差异或第三方
标识/补丁操作证据。

审计至少应回答：

- 没有抹杀事务时，补丁是否改变无关单位的状态？
- 候选对象通过了哪一种身份或因果准入？
- 选择时的终局基线是否只包含实际参战对象，休眠预载对象能否被数量或延迟激活？
- 终局屏障是否单向推进，且只在原版胜利结算期间拒绝矛盾的玩家死亡请求？
- 是否存在只凭模型类型或槽位准入的路径？
- 是否调用 Harmony 拆补丁 API 或显式覆盖优先级？
- 是否引用、查找或包含第三方模组标识？
- 私有成员或 IL 结构不匹配时，是停止初始化还是继续执行未知补丁？
- 原版死亡、移除和结算路径与最终收敛兜底的先后关系是什么？
- 所声称的编译、静态、headless、实机和联机验证分别完成了哪一层？

运行 `tools/run_full_audit.sh` 会重新执行测试、分别构建两个游戏版本，并从最终
DLL 生成 `audit/generated/` 下的机器可读报告。
